# Differences from Express 5.3.0

An app gets the same responses as on Express 5.3.0, except where 5.3.0 crashes the process or has a bug the fork fixes (see below). What else the fork changes is how Express is built, tested and typed, and opt-in additions. What comes next is in the [roadmap](./roadmap).

The full list is the "Unreleased (fork)" section of [History.md](https://github.com/abedmurrar/express/blob/master/History.md).

## Runtime

- **Node.js 22, 24 and 26 only.** `engines` is `>= 22`. Express 5.3.0 supports Node.js 18 and later. CI runs the three supported versions on Linux and Windows.
- **Our own copies of `router`, `send`, `serve-static`, `qs`, `body-parser`, `negotiator` and `accepts`.** `router` 2.3.0, `send` 1.2.1, `serve-static` 2.2.1, `qs` 6.17.1, `body-parser` 2.4.0, `negotiator` 1.1.0 and `accepts` 2.0.0 are vendored into `lib/router`, `lib/send`, `lib/serve-static`, `lib/qs`, `lib/body-parser`, `lib/negotiator` and `lib/accepts`, with their licences and test suites, so routing, file-sending, query-parsing, body-parsing and content-negotiation bugs can be fixed in the fork. They're the same versions Express 5.3.0 installs (it was released with `router` 2.2.0, and a fresh install gets 2.3.0), and `express.static` now uses the same `send` as `res.sendFile` and `res.download`. The extended query parser and `express.urlencoded({ extended: true })` use our `qs`, which needs no dependencies (it uses `WeakMap` and `Map` in place of `side-channel`). See [VENDORED.md](https://github.com/abedmurrar/express/blob/master/VENDORED.md).
- **A throwing `headers` listener no longer crashes the process.** A bad value in the `headers` option of `res.sendFile` or `res.download` (a CR or LF, or an invalid header name), or an `express.static` `setHeaders` function that throws, used to throw inside a file-stat callback and end the process on Express 5.3.0. The error now goes to the callback, or to `next(err)` and the app's error handler.
- **`app.listen()` doesn't swallow later server errors.** Its startup `error` listener is removed once the server is listening, so a later `error` reaches the app's listeners, or is thrown when there are none, as with `http.createServer()`. Express 5.3.0 silently dropped the first one.
- **Files that stat as 0 bytes but have content are sent.** Linux `/proc` and `/sys` files go out whole through `res.sendFile`, `res.download` and `express.static`, with no `Content-Length` and no ranges. Express 5.3.0 sent them empty. Really empty files are sent as before.
- **No per-request prototype swap on `app.listen()` servers.** The server makes `req` and `res` with the app's prototypes already set, so `app.handle()` has nothing to swap. Apps see the same objects as before. The only visible difference: code that runs before the app on that server, such as an `upgrade`, `connect` or `checkContinue` listener, now gets `req` and `res` that already have the app's prototypes.
- **`res.send` sends binary bodies byte for byte.** An ArrayBuffer, SharedArrayBuffer, DataView or any typed array is sent as the bytes it covers. Express 5.3.0 sent an ArrayBuffer as `{}`, a DataView as nothing, and a `Uint16Array` or `Float64Array` one byte per element, or answered 500.
- **`res.set` keeps an unknown Content-Type as given.** `res.set('Content-Type', 'custom-type')` sends `custom-type`, where Express 5.3.0 sent `false`. `res.send`, `res.json` and `res.sendFile` then keep it too, where 5.3.0 used their default type.
- **`res.redirect` sends no Content-Length with Transfer-Encoding**, as `res.send` already did, so clients accept the response.
- **`res.cookie` honours `expires: 0`** with a `maxAge`: the cookie gets `Max-Age` and no `Expires`. The `CookieOptions` type takes only a `Date`, as `@types/express`'s does, so TypeScript code needs a cast for `0`.
- **`res.jsonp` falls back to JSON** when the callback name has no allowed characters, instead of sending JavaScript that doesn't parse.
- **`res.sendFile` and `res.download` honour a per-call `etag` option.** The app's `etag` setting is only the default, and the options object you pass is no longer changed.
- **`res.render` after another response no longer crashes the process.** Without a callback, the "headers already sent" error goes to the error handler. Express 5.3.0 threw it from a deferred callback and ended the process.
- **The "headers already sent" error names the method.** A second `res.send()`, `res.json()`, `res.redirect()` (or any other method that sets a header) after the headers were sent throws Node's `ERR_HTTP_HEADERS_SENT` as before, with `: res.json() was called after the response headers were sent` added to Node's message. The error object, its class, `code` and stack frames, and where it is thrown or passed to `next(err)`, are unchanged; only code that compares the whole message with Node's text sees a difference.
- **`res.render` leaves its options object alone.** `res.locals` is merged into a copy, so a frozen options object works and a shared one isn't changed.
- **A view name ending in `.` gets the usual lookup error** through the callback, where Express 5.3.0 threw a `require('')` error synchronously.
- **View extensions match engines whatever their case.** An engine registered as `HTML` renders `user.html`; Express 5.3.0 missed it and tried `require('html')`. An engine registered in the same case still wins, `app.engines` keeps the keys as registered, and file names keep their case.
- **`res.links` with nothing to add leaves the `Link` header alone.** `res.links({})` sends no `Link` header, and a relation given an empty array adds no entry. Express 5.3.0 sent an empty `Link` header, or one ending in `, `.
- **`res.append` keeps an existing empty header value.** After `res.set('X-A', '')`, `res.append('X-A', 'b')` sends both values, as two header lines. Express 5.3.0 replaced the empty value.
- **`res.redirect` names a status without a standard message by its number.** `res.redirect(399, '/next')` says `399. Redirecting to /next`, where Express 5.3.0 said `undefined. Redirecting to /next`.
- **A quoted `;` in a type parameter stays in its value.** `normalizeType('text/plain; foo="a;b"')` from `express/lib/utils` gives `foo` `"a;b"`, where Express 5.3.0 gave `"a`. Responses don't change.
- **RegExp paths with `g` or `y` match on every request.** In Express 5.3.0 such a RegExp kept its `lastIndex` between requests and matched only every other request, which let requests past a guard like `app.use(/^\/admin/g, auth)`. The fork starts every match at index 0.
- **A mount path made only of slashes keeps its slashes.** In Express 5.3.0, `app.use('//', router)` (or `///`) matched every request, because the trailing slashes were trimmed to an empty path, so the router answered `/secret` before the app's own guards. In the fork a `//` mount answers only `//` and `//` followed by `/...`, and `app.get('//', ...)` no longer answers `/`.
- **Mounting a router on itself at `/` throws.** `router.use(router)`, or a cycle through other routers mounted at `/`, throws a `TypeError` at mount time. Express 5.3.0 accepts it, and any request the router doesn't answer then overflows the stack. Cycles through a mount at another path, which end, still work.
- **A `#` fragment in the request target is dropped before routing.** Node passes it through in `req.url`, and Express 5.3.0 then parsed `//user@host/admin#z` as a URL with a host and routed `/admin`. The fork drops the fragment from `req.url` and `req.originalUrl` first, so a request is routed and read as if the fragment had not been sent.
- **A strict router's `''` route answers its mount path.** With `app.use('/dir', express.Router({ strict: true }))`, the router's `get('')` answers `GET /dir` and not `GET /dir/`. In Express 5.3.0 the strict router saw `/` for both, so a `''` route never matched. A route for `/` still answers both, as in 5.3.0, unless the router opts in with `strictMount` (see Additions).
- **A `req.url` rewritten inside a mount keeps its slash.** With `app.use('/app', router)`, when the router sets `req.url = '/index.html'` for `GET /app` and passes the request on, the layers after it get `/app/index.html`. Express 5.3.0 gives them `/appindex.html`, unless it is installed with router 2.3.0, which has the same fix.
- **An undecodable route parameter's error has `statusCode` 400 too.** Express 5.3.0 sets only `status` on it (router 2.3.0 sets both), so `JSON.stringify(err)` shows one more property.
- **`router.use(subApp)` gives the caller its prototypes back.** When a sub-app mounted with `router.use()` (or called as middleware inside another app) passes the request on, `req` and `res` get the calling app's prototypes back, as `app.use()` already did, so the middleware after it sees the caller's `req.app` and settings (`trust proxy`, for example). In Express 5.3.0 they kept the sub-app's. A bare router outside any app keeps the sub-app's, as before.
- **Userinfo in the `Host` header is dropped.** In Express 5.3.0, `Host: admin.example:x@public.example` gave `req.hostname` `admin.example`, which let a request past a host-based guard. The fork uses the host after the last `@`, for the `Host` header and a trusted `X-Forwarded-Host`, and a host whose port is not all digits gives `req.host` and `req.hostname` `undefined`.
- **A trusted `X-Forwarded-Proto` is lowercased.** `HTTPS` gives `req.protocol` `https` and `req.secure` `true`. Express 5.3.0 kept the case, so `req.secure` was `false`.
- **An IPv6 host has no subdomains.** `Host: [::ffff:127.0.0.1]` gives `req.subdomains` `[]`. Express 5.3.0 split the address on its dots.
- **A trailing root dot is not a subdomain.** `Host: tobi.ferrets.example.com.` gives `req.subdomains` `["ferrets", "tobi"]`, as without the dot. Express 5.3.0 counted the empty label after it and gave `["example", "ferrets", "tobi"]`.
- **Fewer dependencies.** The `merge-descriptors`, `once` and `wrappy` packages are gone, replaced by short built-in equivalents with the same behaviour. With `body-parser` and `qs` vendored, `qs` and the 18 packages it brought (`side-channel` and its chain) are gone too: a production install has 38 packages instead of 58.
- **Content negotiation remembers parsed headers.** Our `negotiator` keeps each parsed `Accept`, `Accept-Charset`, `Accept-Encoding` and `Accept-Language` header (at most 100 of each), so `req.accepts*` and `res.format` don't parse a header they have seen again. The answers are the same as negotiator 1.1.0's for any header and any list of offered values (a property test checks that).
- **Project links** in `package.json` point to the fork, and upstream's `funding` entry is removed.
- **Built-in TypeScript types.** The package ships types ported from `@types/express` 5.0.6 and `@types/express-serve-static-core` 5.1.3, so `@types/express` is no longer needed and code written for it compiles unchanged. See [Install the fork](./install#typescript).
- **An ES module entry.** `import` loads `index.mjs`, a thin wrapper over the CommonJS build with the same named exports Node gives Express 5.3.0, so `import` and `require` share one copy of Express. `package.json` now has an `exports` map; it keeps `require('express')`, `require('express/lib/...')` and `require('express/package.json')` working, and other paths inside the package can no longer be required.

## Additions

Opt-in: an app that doesn't use them behaves as on Express 5.3.0.

- **The `view engines` setting.** `app.set('view engines', ['pug', 'html'])` lets `res.render('page')` render `page.pug` or `page.html`, whichever exists first, after the `view engine` extension. A name with an extension that has no engine, such as `user.profile`, gets one added. When nothing is found, the error lists the extensions tried. See [Several template engines](/api/application#several-template-engines).
- **`req.originalRoute`.** The full path pattern of the route that matched, mount paths included: `'/api/users/:id'` for `router.get('/users/:id')` under `app.use('/api', router)`, through nested routers and sub-apps. It is `undefined` before a route matches and when a RegExp path was involved, and stays set as long as `req.route` does, so error and 404 handlers see the route that failed or passed the request on. It is built when read. See [req.originalRoute](/api/request#reqoriginalroute).
- **Route warnings.** With `DEBUG=express:router`, the router warns when a path no request can match is registered (a raw space, control or non-ASCII character, `?` or `#`, or no leading `/`), and when the same method and path is registered twice on one router. See [Route warnings](/guide/debugging#route-warnings).
- **`req.signal`.** An `AbortSignal` that aborts when the client goes away before the response has finished, for `fetch`, database drivers and timers. It is made on first read, never aborts after a finished response, and behaves the same on Node.js 22, 24 and 26, where Node's own `IncomingMessage#signal` is missing (22) or, before 24.20 and 26.7, also aborts after a finished response. See [req.signal](/api/request#reqsignal).
- **`app.error()` and `router.error()`.** Add error handlers, with an optional path as `app.use()` takes, that run only for an error, whatever the number of parameters the function declares. A handler without `next`, or one that a wrapper, `bind`, a default or rest parameter, a compiler or a minifier gave a `length` other than 4, no longer turns into a normal middleware. Error handlers of four parameters added with `app.use()` work as before. In TypeScript, `router.error()` is on what `express.Router()` returns (`RouterWithErrorHandlers`), not on the `Router` type, which stays as it was. See [app.error()](/api/application#apperror).
- **`app.listRoutes()` and `router.listRoutes()`.** List what is registered on an app or a router, one `{ path, methods, router }` entry per path: routes with their methods, and mounted routers and apps. Nested ones are not expanded; call `listRoutes()` on an entry's `router`. Listing never changes how an app routes: the entries are copies, and no app's router is created, so a sub-app's routing settings can still be set. `router.listRoutes()` is router 2.3.0's, which doesn't list mounted apps. See [app.listRoutes()](/api/application#applistroutes).
- **Strict routing on the mount path.** `express.Router({ strict: true, strictMount: true })`, or the `strict mount routing` setting with `strict routing` on a sub-app, makes a request with nothing after the mount path (`/dir` under `app.use('/dir', router)`) match only routes for `''`, so a route for `/` answers `/dir/` and not `/dir` (#2281). Without it, a strict router's `/` route answers both, as in Express 5.3.0. See [Router()](/api/router#router).
- **Error codes.** Every error Express creates has a stable `code`, such as `EXPRESS_ERR_VIEW_NOT_FOUND`, so error handlers can branch on it instead of on the message. The property isn't enumerable, so serialised and logged errors look as on Express 5.3.0, and errors that already had a code (`ENOENT`, `ERR_HTTP_HEADERS_SENT`) keep it. See [Error codes](/api/errors).
- **Diagnostics channels.** Every middleware, route handler, error handler and `app.param()` callback is traced through the `express.router.request` `TracingChannel` (start, end, asyncStart, asyncEnd and error, with `req`, `res`, the handler, the matched pattern and the error), the same channel and payload as router 2.3.0, so APM subscribers written for it work unchanged; `express()` publishes `{ app }` on `express.initialization`. Nothing runs without subscribers. See [Diagnostics channels](/api/diagnostics).

## Deprecations

The fork's 6.x line removes or changes a few things an app on Express 5.3.0 can call or rely on (see "Our 6.0" in the [roadmap](./roadmap)). Where the app's own code can tell, the compatible line keeps the old behaviour and prints a deprecation warning, as Express itself always has: through `depd`, to stderr, as `express deprecated <message> at <file>:<line>:<column>`. `node --no-deprecation` or `NO_DEPRECATION=express` turns them off, `--trace-deprecation` adds a stack trace, and a `process.on('deprecation')` listener gets them instead of stderr.

The ones that can fire on every request print once per process, at the first call site; the others once per call site.

| Warning | When | Before moving to 6.x | Prints |
|---|---|---|---|
| `res.send(object): Use res.json(object) instead` | `res.send()` with an object, array, number or boolean, which it sends as JSON (#2249). 6.x keeps sending it | Use `res.json()` | once per process |
| `res.set('Content-Type', 'json'): Use res.type('json') instead` | `res.set('Content-Type', value)` with a file extension instead of a type, which is looked up (#7145). 6.x sets the value as given | Use `res.type()`, or the full type | once per process |
| `app.set('trust proxy', 1): a hop count throws in 6.x; ...` | `trust proxy` set to a number (#6541) | List the proxies' addresses or subnets, such as `'loopback, 10.0.0.0/8'` | once per call site |
| `req.get('referer'): this request has different Referer and Referrer headers; ...` | A request has both headers, with different values; `req.get()` returns `Referrer` (#3951). 6.x returns `Referer` | Read the header you mean from `req.headers` | once per process |
| `req.query: the query string has more than 1000 parameters ...` | The `simple` or `extended` parser dropped parts after the first 1,000 (#5878). 6.x answers `400` | Nothing in code: clients that send this many parameters get a 400 on 6.x | once per process |
| `render callback threw on a missing view: ...` | A `res.render()` or `app.render()` callback throws on a missing view, which reaches the error handler because the callback runs before `render` returns. 6.x looks views up asynchronously, where the throw ends the process | Pass the error to `next(err)` | once per call site |
| `Provide a url argument`, `Url must be a string`, `Status must be a number` | `res.redirect()` without a URL, or with arguments of the wrong type (Express 5.3.0 prints these too). 6.x throws | Pass `res.redirect([status,] url)` | once per call site |
| `router deprecated handlers that are Promise-like are deprecated, ...` | A handler or `router.param()` callback returns a thenable that isn't a `Promise` (router 2.2.0 prints these too). 6.x treats it as a plain value | Return a native `Promise` | once per call site |

## Tests that guard the drop-in promise

- **Differential harness.** Thousands of scenarios (329 written by hand and 3,306 generated from every `res` method and `req` property) run on Express 5.3.0 and on the fork, and must give byte-identical responses and error logs. The method comes from [ultimate-express](https://github.com/dimdenGD/ultimate-express)'s test runner.
- **Ecosystem check.** Ten popular middleware packages (body-parser, cors, helmet, morgan, cookie-parser, express-session, compression, multer, passport, express-rate-limit) run on both and must give byte-identical responses and log lines.
- **Middleware's own test suites.** The test suites of cors, express-session, multer, express-rate-limit, http-proxy-middleware, express-openapi-validator, express-fileupload, express-basic-auth, hpp and express-mongo-sanitize (1,678 tests) run against Express 5.3.0 and against the fork. Every test that passes on 5.3.0 must pass on the fork, and today all of them do.
- **Security test suite.** Checks that an auth guard always runs before the route it protects however the path is spelled, that CR and LF never inject a header, where redirects point, that no request pollutes `Object.prototype`, and that file serving never leaves its root.
- **100% coverage.** Statements, branches, functions and lines of `lib/` are measured with c8 and must stay at 100%, or CI fails.
- **Regression tests for the confirmed bugs.** Each one asserts the correct behaviour. All of them pass.
- **Upstream test PRs.** Eight upstream test-coverage pull requests are ported, keeping their authors.

## Tooling

- **Biome** is the only linter and formatter (no ESLint, no Prettier).
- **A benchmark on every PR** that changes code, against Express 5.3.0, Fastify, Koa, Hono, polka and plain `node:http`. See [Benchmarks](./benchmarks).
- **Fewer installed packages** for development: c8 replaces `nyc` (137 packages), and Biome replaces ESLint (63 packages).
