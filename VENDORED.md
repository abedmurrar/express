# Vendored packages

This fork keeps its own copies of the packages it needs to change. Each one keeps its licence and copyright lines in its folder (MIT, except `qs`, which is BSD-3-Clause). Every change we make to a copy is listed below, so we can re-sync from upstream later.

| `send` | https://github.com/pillarjs/send | 1.2.1 | `096a6148` | `src/send/` | `test/send/` (plus `test/send/fixtures/`) |
| `serve-static` | https://github.com/abedmurrar/serve-static (our fork of https://github.com/expressjs/serve-static) | 2.2.1 | `76312e12` | `src/serve-static/` | `test/serve-static/` (plus `test/serve-static/fixtures/`) |

Why these seven: most of the routing bugs and routing performance work are in `router`. The empty-body bug for `/proc` files (#4944) is in `send`. `serve-static` is vendored so that `express.static` uses our `send` and gets its fixes: with the `send` that the npm package installs, a `setHeaders` function that throws crashes the process.

`qs` is vendored so the extended query parser needs no dependencies: qs's two, `side-channel` (with its chain: `side-channel-list`, `side-channel-map`, `side-channel-weakmap`, `call-bound`, `get-intrinsic` and the rest) and `es-define-property`, are replaced by `WeakMap`, `Map` and `Object.defineProperty`. `body-parser` is vendored so `express.urlencoded({ extended: true })` uses our `qs` too: the npm `body-parser` required the npm `qs`, which kept `side-channel` and its chain installed. With both vendored, a production install has 38 packages instead of 58 (`npm ls --omit=dev --all --parseable` prints 39 lines instead of 59, the first being Express itself): `body-parser`, `qs`, and the 18 packages under `qs` (`side-channel`, `side-channel-list`, `side-channel-map`, `side-channel-weakmap`, `call-bound`, `call-bind-apply-helpers`, `get-intrinsic`, `es-define-property`, `es-errors`, `es-object-atoms`, `function-bind`, `get-proto`, `dunder-proto`, `gopd`, `has-symbols`, `hasown`, `math-intrinsics` and `object-inspect`) are gone.

`negotiator` is vendored so it can remember parsed `Accept`, `Accept-Charset`, `Accept-Encoding` and `Accept-Language` headers (see its edits below): re-parsing the header was most of what `req.accepts()` cost. `accepts` is vendored so `req.accepts*` and `res.format` use our `negotiator`: the npm `accepts` requires the npm `negotiator`.

Six of the copies are the same versions Express 5.3.0 installs here, and match the installed packages line for line except for the edits listed below. `router` is one release ahead of the `express-baseline` here, which stays pinned to router 2.2.0, the one Express 5.3.0 was released with (a fresh `npm install express@5.3.0` now gets 2.3.0).

`serve-static`'s source is our fork, https://github.com/abedmurrar/serve-static, created from expressjs/serve-static with only its default branch. Nothing is pushed to it yet: its `master` is upstream's, and the vendored code is upstream's tag `v2.2.1` (commit `76312e12c2754c226a685201ff43d785455d0590`, which the fork's `master` contains; the fork has no tags). Upstream's `master` has one later change to `index.js`, a comment typo fix (`fall-though` to `fall-through`, expressjs/serve-static#246), which is not released and not in our copy.

`router` was first vendored at 2.2.0 (`e6d6b60`) and re-synced to 2.3.0 (tag `v2.3.0`, commit `d4f4d863`, published 2026-11-17) by hand. `express.static` is our `lib/serve-static`, which loads our `lib/send`, so `express.static`, `res.sendFile` and `res.download` all use the same `send`. The `serve-static` package (and the npm `send` it brings) is no longer a dependency; npm still installs both for the development-only `express-baseline` (Express 5.3.0, the differential harness's baseline).

## Changes from upstream

### router

- `src/router/index.js`: added `const { Buffer } = require('node:buffer')` to match Express's lint rule against the global `Buffer`. No behaviour change.
- `src/router/index.js`: renamed two function names so no file has two functions with the same name, which the coverage merge (`lcov` 2) rejects. `Router.prototype.handle` is now `function handleRequest`, and the inner `param` helper in `processParams` is now `nextParam`. Property names are unchanged; only stack-trace frame names differ. The route layer's handler keeps the name `handle`, because tools read it through `layer.name`.

- `src/router/index.js`: the function used as `Router.prototype` is now named `RouterPrototype`, so c8's lcov report doesn't list two functions called `Router`, which breaks the CI coverage merge. It also carries a `/* c8 ignore next */`, because it exists only so routers inherit from `Function` and is never called. Upstream marked it with `istanbul ignore` for the same reason.
- The three files are strict TypeScript: `src/router/lib/layer.ts`, `src/router/lib/route.ts` and `src/router/index.ts`. Only types were added: the statements, their order, the function names and the comments are upstream's, and the compiled `lib/` files differ from the JavaScript build only in the lines below. When re-syncing, apply upstream's JavaScript changes to these files and type the new lines the same way. Dependencies are loaded with `require` and typed with `typeof import(...)`, and the types each file exports (the request and response views, the handler types and the `Layer`, `Route` and `Router` interfaces) are declared after the `require` lines. `RouterRequest` and `RouterResponse` are aliases of Express's `Request` (`src/request`) and `ExpressResponse` (`src/response`), imported with `import type`, so the compiled router requires nothing from Express except `src/error-code` (see the error codes edit below). The lines that read differently from upstream:
  - `layer.ts`: the prototype methods are assigned through `const proto = Layer.prototype as Layer` (`proto.handleError = ...` instead of `Layer.prototype.handleError = ...`), because a function declaration's `prototype` is untyped. The no-`new` call is `new (Layer as LayerConstructor)(path, options, fn)`. `err.status = err.statusCode = 400` in `decodeParam` goes through a typed `const httpError = err as URIError & { status: number; statusCode: number }`. `decodeParam` and `loosen` gained overload signatures, so their JSDoc comments sit above those.
  - `route.ts`: the prototype methods are assigned through `const proto = Route.prototype as Route`, including the generated ones (`proto[method] = function (handler) {...}`). `methods` is cast to the `HttpMethod` union. The flattened handler lists are declared `unknown[]`, and each handler is passed to `Layer` as `fn as LayerHandler` after the existing `typeof fn !== 'function'` check. A few indexed reads carry a cast where the loop bounds already guarantee the value (`stack[idx++] as LayerInstance`, `methods[i] as string`, `this.methods[name as string]`).
  - `index.ts`: the prototype methods are assigned through `const proto = Router.prototype as Router`, which comes right after `Router.prototype = function RouterPrototype() {}` (its `istanbul` and `c8 ignore` comments are unchanged). The no-`new` call is `new (Router as RouterConstructor)(options)`. Inside `Router`, the inner `router` function is cast where TypeScript can't see its prototype: `;(router as Router).handle(req, res, next)` (Biome adds the leading `;`, which compiles to an empty statement), `router.stack = [] as LayerInstance[]` and `return router as Router`. `methods` is cast to `Array<HttpMethod | 'all'>`. `processParams` declares `key`, `paramVal`, `paramCallbacks` and `paramCalled` with their set types and casts them where `nextParam` assigns them, because `paramCallback` reads them from a closure. In `next()`, `layerKeys`, `layerParams` and `layerPath` are declared before the matching loop with `!` and set from the layer as soon as it matched (`layer.params as Params`, `layer.path as string`), where 2.3.0 reads them from its match object. `processParams` takes `keys` in 2.3.0's place, and after it `path`, the path the layer matched, for `setMatchedRoute`; it returns when there are no keys, and the rest of it is a new function, `runParams`, right after it, because with the two new arguments V8 no longer inlined the whole (mw10 counted 2.5% more instructions, and 0.1% fewer once split). `getPathname` casts the `parseurl` result to `Url`, keeping upstream's `try`/`catch`. `restore` gained an overload signature (so its JSDoc comment sits above it) and builds its arrays with `new Array<K>(...)` and `new Array<T[K]>(...)`, which compile to the same `new Array(...)`.

- `src/router/lib/layer.ts`: the RegExp matcher sets `lastIndex = 0` before `exec` when the RegExp has the `g` or `y` flag (`const stateful = _path.global || _path.sticky`), so a stateful RegExp path matches on every request instead of every other one. Not in router 2.2.0 or 2.3.0.
- `src/router/lib/layer.ts`: `loosen()` keeps a path made only of slashes (`//`, `///`) instead of trimming it to `""`, which matched every request, so a `//` mount no longer answers `/` (expressjs/express#4557). Ported from pillarjs/router#190 by MOHIT51196, which is still open: the same lines and comment, with Biome's layout. Router 2.3.0 doesn't have it; if upstream merges #190, the re-sync is a no-op here.
- `src/router/index.ts`: `use()` throws a `TypeError` ("argument handler would mount this router on itself at "/", which loops forever") when the path is `/` and the handler is a router that is this router, or mounts it through routers mounted at `/` (expressjs/express#6809). The walk is a new private helper, `mountsAtRoot`, placed in alphabetical order between `mergeParams` and `processParams`; it runs only when a router is mounted. Not in router 2.2.0 or 2.3.0. The open upstream proposals, pillarjs/router#183 and #193, only emit a warning, and flag every cycle, including those through a mount at another path, which end and work; keep ours when re-syncing.
- `src/router/index.ts`: `handle()` drops a `#` fragment from `req.url` when it runs with no `req.originalUrl` yet (the outermost router), before anything reads the URL, so `parseurl` never falls back to `url.parse`, which reads `//user@host/` as a host. Not in router 2.2.0 or 2.3.0.
- `src/router/index.ts`: a strict router routes a request with nothing after its mount path to a `''` route (expressjs/express#3798). When `trimPrefix` adds the leading slash and the removed mount path doesn't end in `/`, it stores the new `req.url` in a module-level `WeakMap`, `addedSlashUrl` (declared after the module variables), and deletes it again in `next()` (a new `slashMarked` flag says whether this router stored it). In `next()`, `noSlash` is true when the router is strict and `req.url` still equals the stored value; then each route layer is matched on `''` first and on the pathname after (`(noSlash && route !== undefined && layer.match('')) || layer.match(path)`), and middleware layers as before. Not in router 2.2.0 or 2.3.0. Since the 2.3.0 re-sync it is inside upstream's `try`/`catch` (pillarjs/router#216), so a custom RegExp that throws on `''` gives its error, where it used to be tried again on the pathname. The open pillarjs/router#189 instead stops a `/api/` mount from matching `/api`, for every router, which changes non-strict apps; not taken. Making a strict router's `/` route stop answering `/dir` is the `strictMount` opt-in below.
- `src/router/index.ts`: the `strictMount` option (expressjs/express#2281), which builds on `addedSlashUrl`. `RouterOptions` and the `Router` interface have `strictMount?: boolean | undefined`. The constructor sets `router.strictMount = true` only when the option is `true`, after `router.stack`, so a router that doesn't ask for it has upstream's own properties. In `next()`, the match line above becomes a ternary: when `noSlash` and the layer is a route, `layer.match('') || (self.strictMount !== true && layer.match(path))`, otherwise `layer.match(path)`; so with the option a route is matched on `''` only. `src/application.ts` passes `strictMount: this.enabled('strict mount routing')` when it creates the app's router. Not in router 2.2.0 or 2.3.0; pillarjs/router#189 (open) changes every `/api/` mount instead.
- `req.originalRoute` (expressjs/express#2501), the full path pattern of the route that matched, read from records the routers keep on the request. Not in router 2.2.0 or 2.3.0. Express defines the getter (`src/express.ts`, on its request prototype, not enumerable); the router only records:
  - `src/router/lib/layer.ts`: two properties set in the constructor, after `this.matchers`. `rawPath` is router 2.3.0's line from pillarjs/router#174 with its comment (the path as registered, nested arrays flattened), and the re-sync kept it. `rawMatchers` is ours: one matcher per `rawPath` entry, the same array as `matchers` unless the path nests arrays, when it compiles the flattened entries too. Matching still uses `matchers`, so a nested array that holds a RegExp still throws when it is registered, as in 2.2.0 (2.3.0 builds `matchers` from `rawPath`, which makes those work). The re-sync kept this (see #207 in the table above), so `rawMatchers` stays.
  - `src/router/lib/symbols.ts` (new): the two request symbols and the record type. Router 2.3.0 adds a file of this name for its `matchedRoute` symbol, which is here too (see the tracing edit).
  - `src/router/index.ts`: `handle()` has one more variable, `entered`. In `trimPrefix`, right before the `debug('%s %s : %s', ...)` line, a layer that is not a `/` mount (`!layer.slash`) stores a record `{ layer, path, noSlash: false, parent }` in `req[mountMatch]` and in `entered` (`parent` is the previous `req[mountMatch]`). `next()`, after forgetting `addedSlashUrl`, puts `entered.parent` back when `entered` is set. Where `next()` sets `req.route`, it also sets `req[routeMatch]` to `{ layer, path, noSlash, parent: req[mountMatch] }`, and nothing ever clears it, as nothing clears `req.route`. The records are plain symbol-keyed properties, as 2.3.0's `req[matchedRoute]` is, so `util.inspect(req)` lists them.
  - `src/router/lib/original-route.ts` (new): builds the string when it is read. For a path array it finds the entry that matched by running `rawMatchers` again on the recorded path (`""` first when `noSlash`, as `next()` does). 2.3.0's `layer.match()` returns the entry as `match.pattern` (pillarjs/router#207, #216); here `match()` doesn't (see #216 in the table above), so the second run stays.
- `src/router/index.ts`: rest parameters instead of copying `arguments` by hand, with each function's `name` and `length` unchanged (a rest parameter doesn't count toward `length`). `use(handler, ...rest)` flattens `[handler, ...rest]`, or `rest` when the first argument is the path, instead of `slice.call(arguments, offset)`; the generated `Router#VERB` functions take `(path, ...handlers)` and pass `handlers` on; `restore(fn, obj, ...props)` and `wrap`'s `proxy(...args)` build their lists from the rest parameter; and the OPTIONS branch of `handle()` uses `methods.push(...route._methods())` instead of `methods.push.apply(...)`. The module-level `slice` is gone. Measured with valgrind's instruction count: `Router#VERB` registration 0.7% and an OPTIONS request 1.7% fewer instructions, `use()` unchanged. `route.ts` keeps `flatten.call(slice.call(arguments), Infinity)`: `flatten.call(arguments, Infinity)` counted 0.8% more, and a rest parameter can't tell `route.get()` from `route.get(undefined)` (two different errors) while keeping `length` 1. Not in router 2.2.0 or 2.3.0.
- Registration-time warnings on the `express:router` debug namespace, for a path no request can match (expressjs/express#2511) and for the same method and path registered twice on one router. Not in router 2.2.0 or 2.3.0. `src/router/lib/warnings.ts` (new) does the work, only while `express:router` is enabled. `src/router/index.ts`: `use()` calls `checkPath(path, 'use')` after its loop, and `route()` calls `checkPath(path, 'route')` and `trackRoute(this, route, this.stack.length - 1)` after pushing the layer. `src/router/lib/route.ts` requires `methodAdded` from `./warnings`, and `all()` and each method call `methodAdded(this, method)` (`'all'` for `all()`) before `return this`.
- `router.error()` (expressjs/express#2896): `use()` for error handlers, which run only for an error whatever their `length`. Not in router 2.2.0 or 2.3.0 (pillarjs/router#59, open since 2017, proposed it along with deprecating the length check, which we keep). `src/router/lib/layer.ts`: the `Layer` interface has `errorOnly: boolean`, set to `false` on the prototype after `const proto = Layer.prototype as Layer` (so layers that don't use it get no own property); `handleError` now passes the error on when `fn.length !== 4 && !this.errorOnly` (was `fn.length !== 4`), and `handleRequest` passes the request on when `fn.length > 3 || this.errorOnly` (was `fn.length > 3`). `src/router/index.ts`: the `Router` interface has `error()`, and `proto.error` (after `proto.use`) calls `this.use(...)`, then sets `errorOnly` on the layers it added, or removes them all and throws `EXPRESS_ERR_ERROR_HANDLER_IS_ROUTER` when one of them is a router or an app (a function with a `handle` method). When re-syncing, keep the two conditions and `proto.error`; `route.ts` is untouched.
- Error codes (expressjs/express#6951): every error the router creates gets a stable `code` from Express's `withCode` helper (`src/error-code.ts`, required as `../error-code` from `index.ts` and `../../error-code` from `lib/layer.ts` and `lib/route.ts`), which defines `code` as a writable, configurable, non-enumerable own property on the error the call site just created, so messages, classes and stack frames stay upstream's. Not in router 2.2.0 or 2.3.0. `index.ts`: the four `param()` checks (`EXPRESS_ERR_PARAM_NAME_REQUIRED`, `EXPRESS_ERR_PARAM_NAME_NOT_STRING`, `EXPRESS_ERR_PARAM_CALLBACK_REQUIRED`, `EXPRESS_ERR_PARAM_CALLBACK_NOT_FUNCTION`), `handle()` without a callback (`EXPRESS_ERR_ROUTER_CALLBACK_REQUIRED`), `use()` without a handler or with one that isn't a function (`EXPRESS_ERR_HANDLER_REQUIRED`, `EXPRESS_ERR_HANDLER_NOT_FUNCTION`), our mount-on-itself check (`EXPRESS_ERR_ROUTER_MOUNTS_ITSELF`), our `error()` given a router or an app (`EXPRESS_ERR_ERROR_HANDLER_IS_ROUTER`) and the `Rejected promise` error of a param callback (`EXPRESS_ERR_REJECTED_PROMISE`). `lib/route.ts`: the same two handler checks in `all()` and in each method. `lib/layer.ts`: the two `Rejected promise` errors (`handleRequest`, `handleError`), and `decodeParam`'s 400 `URIError` (`EXPRESS_ERR_PARAM_DECODE_FAILED`, set after its `status`). When re-syncing, wrap any new `new Error`/`new TypeError` the same way and add its code to docs/api/errors.md (the `fork-error-codes` tests check the list).

- Tracing (`diagnostics_channel`), ported from router 2.3.0 before the re-sync: the `express.router.request` TracingChannel of pillarjs/router#196, with the matched pattern of #207, the parameter callbacks and error attribution of #215 and the terminal-event rules of #223. Same channel name, events and context, and the re-sync kept this code. `src/router/lib/tracing.ts` (new) is 2.3.0's `lib/tracing.js` typed, plus its `lib/param.js` (`callParam`) as a private helper that only the traced path uses; it exports the `TraceContext` type, and requires `node:diagnostics_channel` without 2.3.0's `dc.tracingChannel &&` guard and `shouldTrace()` (Node 22 has `tracingChannel` and its `hasSubscribers`). `src/router/lib/symbols.ts`: 2.3.0's `matchedRoute` symbol. `src/router/lib/layer.ts`: `handleError` and `handleRequest` are unchanged; two new methods after them, `traceError` and `traceRequest`, do the same with 2.3.0's traced path (the not-a-handler checks, then 2.3.0's `invokeWithTrace` call with its context), and `invokeWithTrace` (2.3.0's) follows them. Their callbacks are named `invokeErrorHandler` and `invokeHandler` (anonymous upstream; lcov rejects their duplicate inferred names). `src/router/index.ts`: `handle()` checks `requestChannel.hasSubscribers` once (`var traced`, after the `restore` line: a `var`, so `next()` and `trimPrefix` read it without a temporal-dead-zone check), and when traced wraps `done` in a second `restore` for `req[matchedRoute]`; when traced, `trimPrefix` sets `req[matchedRoute]` with the new `setMatchedRoute` helper (placed before `mergeParams`) and calls `traceError`/`traceRequest` instead of `handleError`/`handleRequest`; a route's own layer always gets `handleRequest` (`route.dispatch` traces its handlers); when traced, `next()` calls `setMatchedRoute` for a matched route, in the block that sets `req.route` (not in the `processParams` callback, which would make `noSlash` a context variable that the matching loop reads for every layer); `next()` records `err`, and the loop records a matching error, with `recordError`; and `paramCallback` calls `setMatchedRoute` and `traceParam` when there are subscribers. `src/router/lib/route.ts`: `dispatch()` checks once (`var traced`, requiring `requestChannel` from `./tracing`), and its `next()` calls `traceError`/`traceRequest` when traced. How this copy differs from 2.3.0:
  - The subscriber check is made once per router and once per route as they start on a request, and picks each layer's traced or untraced method, where 2.3.0 checks inside `handleError` and `handleRequest` before every handler (with the traced call's closure in them) and sets `req[matchedRoute]` in `next()` for every matched layer, and restores it, on every request. Here it is set only while traced, right before the parameter callbacks or the handler run. 2.3.0's way counted 0.5% to 1% more instructions per request with no subscribers (hello +0.48%, mw10 +1.05%), over the 0.3% budget; with the check moved out but the traced path still inside the two methods, mw10 was still +0.43%. A subscriber that attaches during a request is seen from the next router or route the request enters. Keep this when re-syncing.
  - The untraced paths are 2.2.0's, unchanged: 2.3.0 rewrote them around a `handlePromise` helper and `callParam`, passing a no-op instead of `null` to a returned promise's `then`, so a broken thenable that calls `then`'s first callback without checking it no longer gets a `TypeError` to `next()`. Here that change only applies while traced (`invokeWithTrace` and `callParam` pass functions, as 2.3.0 does). The re-sync left it so: only a broken thenable can tell.
  - Errors are recorded only while the channel has subscribers (`requestChannel.hasSubscribers` before both `recordError` calls in `index.ts`), so an untraced request gets no `Symbol.for('router.tracing.publishedErrors')` set. 2.3.0 records every error, so a subscriber that attaches while an error is already on its way can't blame a forwarder; here that's covered when the error passes a router or reaches an error handler after the subscriber attached (2.3.0's tests for it pass), and missed only if it did both before. ### negotiator

The source is upstream's tag `v1.1.0` (commit `14b0a7b88e7e7bb1cae38681195951bff29ca2fd`), whose `index.js` and `lib/*.js` are identical to the npm package's. `src/negotiator/LICENSE` is upstream's `LICENSE` (MIT), copied into `lib/negotiator/` by `scripts/build.js`. The layout is upstream's: `src/negotiator/index.ts` and `lib/accept.ts`, `charset.ts`, `encoding.ts`, `language.ts` and `mediaType.ts`. Upstream's `README.md`, `HISTORY.md`, benchmarks and examples are not copied.

- **The cache (not in upstream).** Each of the four parsers, `parseAccept` (`mediaType.ts`), `parseAcceptCharset`, `parseAcceptEncoding` and `parseAcceptLanguage`, looks the header string up in its own `Map` first and returns the list it parsed before; on a miss it parses as upstream does and stores the result through `remember(key, value)`. Each map holds at most `CACHE_LIMIT` (100) entries, the constant style of `remember()` in `src/utils.ts`. Unlike there, a full map is replaced with `new Map()` instead of emptied with `clear()`: a long-lived map is in V8's old generation, `clear()` allocates its new table there too, and the tables it leaves behind keep every list put in them alive through the minor collections until the next full one. With a different header on every request, that made each parse about 3 µs slower (scavenges took 2.4 s instead of 0.12 s over 800,000 calls). The map variables are therefore `var`, not `const`.
  - Only the parsed specs are cached, never an answer for a list of provided values: `preferredMediaTypes` and the other three still match every provided value against the specs on each call.
  - The cached list is frozen (`Object.freeze`), so an in-place sort or edit fails loudly instead of changing what the next caller gets. The specs in it are not frozen. After parsing, negotiator only reads them (`specify`, `compareSpecs`, `getFull*` and `isQuality`; `filter` makes the copy that `sort` sorts), and they never leave the file: callers get new arrays of strings or of their own provided values. Freezing each spec cost about 1 µs per new header. The property test in `test/property/negotiation.js` compares every answer with the npm negotiator 1.1.0, so a later edit that wrote to a cached spec and changed an answer would fail it.
  - A header that isn't a string (only possible when code sets `req.headers` itself) is not stored, so it is parsed every time, as before. An `undefined` header still takes upstream's defaults (`*/*` for `Accept`, `*` for `Accept-Charset` and `Accept-Language`, `''` for `Accept-Encoding`), which are cached like any other string.
- `mediaType.ts`: upstream's `==` and `!=` in `specify` are `===` and `!==`, for the repo's lint rule. Every operand is a string or `undefined` (the type and subtype, and parameter values or `'*'`), so the comparisons give the same results.
- `charset.ts`, `language.ts` and `mediaType.ts`: `compareSpecs` ends in upstream's `|| 0`, which can't be reached (two specs or priorities always differ in `i`, their position in the header or in the provided list), so its line carries `/* c8 ignore next */`.
- The files are strict TypeScript with no `any`. Only types were added: the statements, their order, the `var` declarations, the function names and the comments are upstream's (with the edits above). When re-syncing, apply upstream's JavaScript changes to these files and type the new lines the same way. Dependencies are loaded with `require` and typed with `typeof import(...)`, and each file loads the others typed by the type it exports: `ParseAcceptHeader` (`accept.ts`), `PreferredCharsets`, `PreferredEncodings`, `PreferredLanguages` and `PreferredMediaTypes`. `index.ts` exports `Negotiator`, `NegotiatorConstructor`, `NegotiatorRequest` and `NegotiatorEncodingOptions`. The lines that read differently from upstream:
  - `index.ts`: the prototype methods are assigned through `const proto = Negotiator.prototype as Negotiator` (`proto.charset = ...`, and the backwards-compatible aliases `proto.preferredCharset = proto.charset` and the rest). The no-`new` call is `new (Negotiator as unknown as NegotiatorConstructor)(request)`. `charsets` reads `this.request.headers['accept-charset'] as string | undefined` (Node's header types allow an array there; Node joins repeated headers into one string).
  - The four parsers: the list from `parseAccept` is declared `Array<ContentType | Spec>`, because upstream overwrites each parsed value with its spec in the same array; `accepts[i] as ContentType` is passed to the formatter, and the list is returned `as Spec[]`.
  - The priority loops read `accepted[i] as Spec`, and `getType` and the other provided-list mappers return `provided[...] as string`.
  - `compareSpecs` takes two priorities and reads `(a.i as number) - (b.i as number)` (upstream's starting priority has no `i`). The no-provided-list path sorts specs, which have no `s` or `o`, with the same function (upstream relies on `NaN` there), so it is passed as `compareSpecs as unknown as (a: Spec, b: Spec) => number`, and `encoding.ts` passes its `comparator` the same way.
  - `encoding.ts`: `hasIdentity` is declared `EncodingPriority | boolean | null`, because upstream assigns it `specify(...)`'s result, and `specify`'s `index` is optional (upstream calls `specify('identity', encoding)` without it).
  - `mediaType.ts`: the `every` callback in `specify` reads `(p as MediaTypeSpec).params[k]`, because `p` is a `var` that TypeScript doesn't narrow inside a callback.
  - `isQuality` takes `{ q: number }`, since it filters both specs and priorities.
  - Every other line gained parameter and return types only.
  - Comments that are ours: the note under "Module dependencies" in each file, the cache comments, the `c8 ignore` comments, and the doc comments on the exported and spec types.
- `content-type` stays an npm package (Express already depends on it). negotiator 1.1.0 needs 2.1.0 or later (the `comma` and `start` parse options), so Express's range is now `^2.1.0`; 2.1.0 is what was installed already.
